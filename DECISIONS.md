# Decisions

Ambiguities met during the structural upgrade, and the conservative option
taken. Numbered by range (see PLAN.md): orchestrator D-001–099, foundation
D-100–199, domain-layer D-200–299, public-feed D-300–399, compliance
D-400–499, backtest D-500–599, rescan D-600–699, reviewer fixes D-700+.

## Orchestrator

**D-001 — Branch name.** The brief says work on `structural-upgrade`; this
session is only permitted to push to `claude/launchtrace-structural-upgrade-8umgor`.
All work is integrated on a local `structural-upgrade` branch and pushed to the
designated remote branch (same commits). `main` is never touched. If you want
the remote branch to be called `structural-upgrade`, that is a one-line push
for a human (HUMAN_ACTIONS).

**D-002 — Stability evidence is generated with network-free providers.** The
2026 journals are replayed against the recorded web evidence in
`data/web_evidence/` and the fixture Companies House registry (the real bulk
index is a 500 MB download, not available offline). That makes the snapshot
deterministic and reproducible on any machine, at the cost of lower absolute
scores than a live run (no company matches for the 2026 journals). It answers
the question it is for — did a code change move any lead — not "what would a
live run produce".

**D-003 — Python 3.11 for all verification**, matching CI and the Dockerfile,
although the sandbox default interpreter is 3.13.

## Foundation (Phase 1)

**D-100 — Alembic in the package, built in code.** The environment is
`src/db/alembic/`; `init_db` builds the Alembic `Config` in code (no ini
needed), so the Docker image migrates itself. Root `alembic.ini` is CLI
convenience and is also copied into the image. `0001_baseline` was
autogenerated from the models as they stood before this phase and reviewed;
`0002_brands` likewise. Revision ids are the explicit strings
`0001_baseline`, `0002_brands`.

**D-101 — Fast path for a brand-new SQLite file.** `init_db` on an empty
SQLite database runs `create_all` + `stamp head` instead of replaying every
revision (≈0.1 s vs ≈0.3 s; the suite and every CLI command call it). A test
proves the resulting schema is identical to `alembic upgrade head` (inspector
comparison and `compare_metadata == []`). PostgreSQL always replays the
migrations. An already-at-head database costs one query.

**D-102 — Pre-Alembic adoption uses a frozen baseline.** `src/db/baseline.py`
lists every baseline table and column. Adoption creates missing baseline
tables (from model copies trimmed to baseline columns), adds missing baseline
columns (the old additive path, now restricted) and missing baseline indexes,
stamps `0001_baseline`, then upgrades. A database that already has every
current table and column (made by `create_all` from current models, e.g. the
test fixture or a database built from the regenerated
`migrations/0001_initial.sql`) is stamped `head` instead. A database in a
half-way state (some 0002 objects but not all) fails loudly rather than being
guessed at. Nothing is ever dropped.

**D-103 — Foreign-key behaviour.** `opportunities.brand_id` and
`score_events.brand_id` are `ON DELETE SET NULL` (deleting a brand must never
delete a lead or its score history). `observations.brand_id` is `CASCADE` (as
PLAN.md says) and so is `stage_changes.brand_id` (not specified; a stage change
means nothing without its brand). FK constraint names are explicit; the two
unique constraints on `brands` take the database's default names, matching
the models.

**D-104 — Stability: one `first_run` entry moved, and that is the bug fix.**
The expected diff was "re_run becomes equal to first_run; first_run
unchanged". All ten re_run entries now equal their first_run. One first_run
entry also changed: `open_data_2018-01-05` BUNK (UK00003272909) gains
`first_trademark_for_applicant`, 11 → 22, still SUPPRESS. Cause: the harness
processes 2026-036/037 *before* 2018-001, and Bunk Group Limited also files in
2026-037 (UK00004435948). The old code counted that 2026 filing as "already
known" when scoring a 2018 journal — a filing from eight years in the
future. `before_journal` fixes exactly that, so this is the same bug, seen
through the harness's out-of-chronological-order processing. Verified by
script; see `reports/stability/phase1_diff.txt`.

**D-105 — Brand identity details.** Applicant normalisation for the `tm:` key
and `applicant_key_hash` is `normalise_company_name` (case, punctuation,
accents and legal suffixes removed); the mark uses `normalise_text`. An
unmatched applicant's different marks are separate `tm:` brands (the key is
mark|applicant, per PLAN.md). If two `tm:` brands later match one company,
only the first gains the company number; no automatic merge (a merge would
change public uids). `brand_name` is NOT NULL, stored as "" when the first mark
had no text.

**D-106 — first/last seen and current state.** `first_seen_at` is the
wall-clock time the brand row was created (when LaunchTrace first saw it) and
never changes. `first_seen_journal` and `first_filing_date` take the earliest
value seen, so a back-filled older journal moves them earlier.
`last_seen_journal` and `current_stage/score/band` are only updated from a
journal at least as new as `last_seen_journal`, so a back-fill does not roll
the current state back. Within one run the best opportunity of a company
(deliverable first, then highest score) sets `current_*`. A stage change is
recorded only when a strictly later journal brings a different stage.

**D-107 — Brands for suppressed opportunities too.** Every opportunity in
`result.opportunities` (all scored records, suppressed included) gets a
brand; records dropped before scoring do not. Backtests and rescans need the
population we rejected.

**D-108 — Observation semantics.** Append-only, no update API. A re-run
appends a fresh set (new `observed_at`); within one `sync_brands` call an
identical (brand, signal, value) is written once. Web signals are recorded
only when a search was attempted (a null value then means "searched, not
found"); Companies House signals only for a confident match. An observation
without `source_date` is stored as not PIT-safe whatever the registry says.
`nice_classes` uses the publication date (classes can be amended before
publication). Unregistered signal names raise `ValueError`.
`observations_as_of(..., pit_safe_only=False)` additionally returns non-PIT
observations observed on or before the cutoff.

**D-109 — Brand sync never loses a run.** `sync_brands` runs inside a
savepoint after `save_opportunities`; if it fails, the run is still recorded
and a warning is added.

**D-110 — Search budget rules.** The guard counts provider calls, not
candidates (one candidate can take two). A record is searched completely or
not at all, and once one record is refused every later one is too, so the cap
is never exceeded and is reached exactly when records need one call each. The
existing `SEARCH_MAX_CANDIDATES_PER_RUN` candidate cap stays as it was.
`Pipeline.run` without a budget (smoke test, direct use) applies the per-run
cap only; the rolling monthly budget is computed in `commands` from
`pipeline_runs` started in the last `window_days` (all modes, blocked runs
included). Fixture and recorded providers are counted like real ones; the
stability harness never reaches the cap (its scores are unchanged). A blank
`SEARCH_MAX_CALLS_PER_RUN` (an unset repository variable) means unset.

**D-111 — Idempotency scope.** The "already processed" early exit applies
only when the run would write to the database (`--no-db` always runs). An
already-processed journal is not re-sent by `weekly --send`; use
`send --run-id`. When the journal cannot be resolved up front, the run goes
ahead and fails closed through the pipeline exactly as before. A blocked or
failed attempt does not mark the journal processed, so the next scheduled
attempt retries it.

**D-112 — Backfill on a fresh database.** `backfill` read the database before
any `init_db`, which crashed on a fresh database; it now initialises first.
It also honours `--force`.

**D-113 — Cache pruning scope.** Only the journal download caches
(`CACHE_DIR/journals`, `CACHE_DIR/opendata`, listed in
`config/operations.json`) are pruned. The Companies House API cache and bulk
index are left alone (they have their own lifecycle). Pruning runs at the end
of every `weekly` invocation, including the "already processed" exit and
failures, and never raises. Not added to `backfill` (not asked for).

**D-114 — Network guard also clears proxy variables.** The sandbox (and some
developer machines) route HTTPS through a loopback forward proxy; allowing
loopback would otherwise let an HTTP client reach the internet. The guard
removes `HTTP(S)_PROXY`/`ALL_PROXY` for each test. Loopback and Unix sockets
stay allowed. No existing test made a network attempt.

**D-115 — PostgreSQL not exercised locally.** PostgreSQL 16 binaries exist in
the sandbox, but starting a server requires running as a non-root user, which
the sandbox refuses. The PostgreSQL DDL for upgrade and downgrade was rendered
offline (`alembic upgrade head --sql`) and reviewed; the CI `migration` job
does the real upgrade → downgrade → upgrade, plus the generated-SQL route in a
second database followed by `init-db`. `tests/test_migrations.py` has a
PostgreSQL round-trip test that runs when `LAUNCHTRACE_TEST_POSTGRES_URL` is
set.

**D-116 — SQLite state between workflow runs.** Without `DATABASE_URL`, the
weekly workflow restores the SQLite file from `actions/cache`
(`lt-db-<run_id>`, restore-keys `lt-db-`), checkpoints the WAL into the file
after the run, saves it, and uploads it as a 14-day artifact. The backfill
workflow is unchanged (no DB carry-over), as before.

## Domain layer (Phase 2)

**D-200 — Where the domain layer sits.** `src/enrich/domain/` runs as stage 6b,
after web enrichment and before scoring, through an injectable `DomainProber`
(`Pipeline(domain=...)`). Without one, `DOMAIN_LAYER_ENABLED` (default `true`)
picks `LiveDomainProber`, else `NullDomainProber`. Tests set
`DOMAIN_LAYER_ENABLED=false` in `tests/conftest.py` (dnspython sends UDP, which
the connect-based network guard would not catch). The smoke test uses
`FixtureDomainProber` over `tests/fixtures/domain/probes.json`;
`scripts/replay_validation.py` uses the null prober (a replay must not depend on
today's internet); `validate` and `weekly` use the live default. The stage is
wrapped twice: a failing probe becomes signals carrying an error, a failing
stage becomes a run warning. Neither ever blocks a run.

**D-201 — Only the verified website is probed.** The domain is the registrable
domain of `opp.web.website` (entity-verified). `candidate_website` is off
(`domain_selection.use_candidate_website: false`): probing an unproven guess
would attach a stranger's registration date and shop to this brand. Domains are
never guessed from brand names. Marketplace, social, retailer, directory and
shared-platform hosts (`skip_hosts`, which now includes tripadvisor/yelp/
trustpilot — the stability harness showed a tripadvisor.com "verified
website"), IP literals and non-public names are never probed. Registrable domain
uses a short list of two-label suffixes in config, not the full Public Suffix
List (no new dependency); an unlisted suffix falls back to the last two labels.

**D-202 — When there is nothing to probe.** No search attempted → no domain
signals at all (`Opportunity.domain` is None): we do not know the website, so we
claim nothing. Search attempted but no verified website → `web_presence_stage`
`no_domain`, `checked=False`, no network call and no observation (it is a web
search finding, not a domain fact). The per-run cap
(`max_domains_per_run`, 60) counts distinct domains; a company's several marks
share one probe. Leads past the cap get `domain_cap_reached` and a run warning.

**D-203 — Politeness and failure rules.** RDAP: IANA bootstrap cached at
`CACHE_DIR/rdap/dns.json` for 7 days (stale cache, then config fallbacks for
.uk/.com/.net, when IANA is unreachable); 8 s timeout; one retry on timeout,
transport error or 5xx; 1 s minimum per RDAP server; a 429 stops that server for
30 s and marks the domain `rdap_rate_limited` (not fetched); a 404 is
`rdap_not_found`. DNS: 3 s lifetime; a timeout is `None` (unknown), never
`False`; NXDOMAIN makes everything `False` and skips the homepage. Homepage:
robots.txt first (401/403/5xx = keep out, other 4xx = allowed; matched for the
token `LaunchTrace` and the full user agent); https then http only if https is
unreachable; 8 s timeout plus a wall-clock budget while streaming; body capped
at 512 KB; at most 5 redirects; one page, no crawling. The `rdap` cache
directory is outside the journal caches that `weekly` prunes.

**D-204 — Platform, holding page and stage.** Fingerprints and phrases live in
`config/domain_layer.json`. Holding phrases count only when no store marker is
present (a live store often says "be the first to know" in its footer); a very
short visible body (< 200 chars) without store markers is a holding page; a
parked page is also a holding page. A homepage redirecting to a marketplace or
social host is stage `unknown` and its platform is not recorded (the page is not
the brand's). A redirect to another ordinary domain is assessed normally
(brands move domains) but recorded as `redirect_target_kind: other_domain`. A
shop platform (Shopify, WooCommerce, Big Cartel, Ecwid) that is not a holding
page counts as `live_store` even without a store marker on the homepage. The CSV
column `shop_platform` carries whatever platform was detected (including
WordPress/Wix/Squarespace), named after the brief; `DomainSignals.shop_platform`
says whether it is a shop platform.

**D-205 — Which domain signals are point-in-time safe.** Only
`domain_created` (RDAP `registration` event, `source_date` = registration date,
source `rdap`). It is a dated historical fact knowable on that date. Caveat: a
domain that lapsed or was dropped and re-registered shows the *latest*
registration date, so it can make a domain look younger than its first use —
never older, and never from the future relative to the observation. Not PIT
safe: `domain_expires` (a future date that moves on each renewal),
`domain_registrar` (domains change registrar), `dns_has_*` (DNS as it is when we
looked), `homepage_status`, `site_platform`, `holding_page`,
`web_presence_stage` (they describe the present site). RDAP "last changed" is
kept on `DomainSignals` but not recorded as an observation (it is overwritten by
each change, so it says nothing reliable about earlier dates). These are stored
with `source_date` None. A failed check writes no observation for that check.

**D-206 — Scoring at weight 0, outside the existing indicator lists.**
`config/scoring.json` gains a separate `domain_indicators` list
(`domain_registered_recently` — registered no more than 365 days before filing,
or after it; `shop_platform_detected`; `holding_page_detected` — not parked;
`has_mx_records`), all weight 0. They are outside `positive_indicators` /
`negative_indicators`, so the existing config tests (positive weights > 0),
the achievable-weight calibration and the missing-evidence scaling are
untouched. The scorer computes them (`domain_indicator_keys`) and the pipeline
lists the ones that fired on `Opportunity.domain.indicators`; a weight-0
indicator adds nothing and produces no `ScoreReason`, so `score.reasons`,
`reason_texts`, emails and the stability snapshot's `reason_keys` do not change.
Proof: the stability harness now injects a fixture prober giving every verified
website (20 probes over the 10 runs) signals that fire all four indicators, and
the compare output is byte-identical to `reports/stability/phase1_diff.txt`.

**D-207 — Persistence without a schema change.** `Opportunity.domain` is not
stored in `opportunities` (no new revision); the facts are in `observations`.
A run rebuilt from the database for `send --run-id` therefore has blank domain
CSV columns, as it already lacks other non-persisted fields.
`brands.website` is unchanged (still the verified website from web search).
